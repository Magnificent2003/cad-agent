## 完整实验结果

**接入与观测成功；场布部分指标改善，但在 1200 秒实验上限内未完成交付。** 与0929客户端采用相同时间上限；本轮约1202.488秒退出（含取消收尾），任务终态 `cancelled`，没有后端新版本，也没有伪造网页下载结果。

实际模型标识始终为 `aiapi-cad/gpt-6.1-sol`。唯一公开用户提示保持不变，原图和运行期间代码指纹不变；21份核心算法文件与本轮开始前逐项一致。没有开发者向对话发送坐标、补充面积、人工建筑名单或替代代码。

共41次工具调用：Skill 2、A 1、图纸查询1、B 8、规则3、通用Python 20、布局2、成果复核4（末次因时间上限返回 Tool execution aborted，不能算完成的复核）。发生一次空答复自动续轮。引擎生成了3次压缩摘要，分别约41.8、50.1、68.5秒，合计160.5秒。工具执行元数据累计约69.4秒；不能用总耗时减去这个数就精确归因于某一组件，余下包括模型生成、压缩、网络、导入和调度。

主要往返有实际原因：

1. B的报告分页参数被用在占地查询/提案请求中，工具拒绝后模型重试；部分错误重复出现。
2. 首批设施面积不足。模型后来读取几何、拆分和扩大设施，没有覆盖原比例来降低目标。
3. 道路与轮廓发生冲突。模型改用通用Python写图，又出现清单指向文字实体、道路用闭合边框表示而无实际DXF宽度等接口不匹配；检查器均明确拒绝。
4. 换成6米宽中心线后，又发现一条道路反向折返及另一条道路距场界仅约0.665米。模型最后拆分折返并内移道路；尚未完成下一次复核，客户端即达到时间上限。

这些失败和纠错已完整保留，不能把工具状态 `completed` 当成工具返回的 `status=passed`，更不能当成任务已交付。

## 判断与后续实验边界

更换模型后，面积任务执行和错误修正有改善，自动交付与道路服务仍不足。尤其AIAPI使用128k项目上下文预算，3次压缩耗时约160.5秒；本轮不是与DeepSeek等上下文预算的严格对照。不能据一次实验宣称“基座模型更强/更弱”，也不能把未交付候选的几何通过包装为完整闭环成功。

后续若继续比较，先核对供应商支持的上下文容量，再选择相同预算和足够的任务时限；随后分别统计规划、工具参数纠错、压缩和交付耗时。道路连通与完整交付的改进另立任务，本轮不改算法、Skill或模型任务提示。

## 收尾时发现的启动问题

本次隔离实验的全部服务和监督进程已经停止，三个实验端口试绑可用。随后检查常用端口时，8000和9875一度报告EADDRINUSE，Linux和Windows的监听查询均为空；Windows IPv4/IPv6排除范围只有50000～50059，portproxy为空，不能把本次冲突归因于已证实的系统端口保留。

进一步查询全部TCP状态，Windows的8000出现 `Bound`（100）以及 `CloseWait`（8），持有PID35004；不是Listen，所以原监听进程回收无法定位它。后续未能稳定查询到该PID名称，不据此指定某个应用为原因。9875自行恢复，8000仍不能监听。

为使日常一键启动可用，补齐已有空闲内部端口回退机制：`scripts/dev.py` 的业务后端在不可定位的绑定冲突下选择后续空闲端口，并设置统一 `CAD_API_BASE_URL`；`frontend/vite.config.ts` 读取此变量，避免代理仍写死8000。可定位的旧监听服务仍按既有授权回收。没有结束未知Windows进程，也没有改WSL或系统端口配置。

真实执行 `bash scripts/dev.sh`：FreeCAD9875、后端自动8001、智能体4096、网页5173全部启动；经网页 `/api/health` 与后端8001得到相同200响应，Agent connected。验证后向本次监督进程发送SIGTERM，由其停止全部子服务。记录见同一实验目录的 `startup-fallback-check.json`，不再发起模型请求。

代表性的两种端口回退校验通过；模型配置/隔离、记录脱敏及运行边界的12项针对性检查通过。以上短检查只验证本轮接入和收尾功能；性能结论仍只取真实v0009任务。已保留源码原有末尾空行（`spatial_report.py`），没有为清理格式而改变核心算法文件指纹。
