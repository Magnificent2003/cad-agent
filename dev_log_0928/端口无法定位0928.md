# FreeCAD 端口无法定位时的后备启动 · 2026-09-28

## 现场与结论

用户连续启动在 9875 上收到 EADDRINUSE，Linux 无监听记录，Windows 未找到可结束的监听者。排查时该端口已经自行恢复：同一机器普通 WSL 入口和工具入口均可 bind/listen；Windows 的 IPv4/IPv6 保留范围为 5357、50000～50059，没有 9875，portproxy 也为空。因此不能将此前原因断言为系统保留端口或遗留监听进程。

确定的代码缺口：FreeCAD 内部 RPC 端口在启动器、插件、MCP 和后端多处固定为 9875；现有清理找不到可终止对象时，只能让整个项目退出。

## 修改

- 保留 Linux／Windows 的冲突监听者清理。
- 无法定位监听者且 bind 仍失败时，针对 FreeCAD 的内部端口选择后续最多 32 个候选中的空闲端口。跳过项目其他服务端口，不杀后备端口上的其他服务。
- 用本轮进程环境 `FREECAD_RPC_PORT` 同步 FreeCAD 插件、MCP 客户端、启动就绪检测和后端状态检查；不把临时选择写回用户配置。默认仍是 9875，网页仍是 5173。
- `.env` 和 `.env.example` 同步增加首选端口字段。只有无可识别监听者的拒绝绑定会触发后备；权限不足、受保护进程、端口配置重复等仍明确报错。
- 不修改 Windows 保留范围、端口转发或 WSL 全局网络配置。场布模块保持启用。

## 实际复现

用一个真实 socket bind(127.0.0.1:9875)，但不调用 listen，复现“EADDRINUSE 且找不到监听进程”。这证明旧清理逻辑存在该类盲区，不证明用户当时一定由这种 socket 导致。

保持该占用存在，执行原来的 `bash scripts/dev.sh`：自动改用 9876，FreeCAD、后端、智能体、Vite 全部启动。FreeCAD startup.json 记录实际监听 9876；后端进程环境为 9876，实际 RPC 状态返回 success/healthy；智能体的 MCP 已连接。相关端口与启动检查通过，没有运行模型场布测试。

额外执行一次无图纸修改的 MCP print 验证时，收到 GUI 排队超时。X11 窗口检查发现 FreeCAD 的 Document Recovery 模态窗口；插件源码会在活动模态窗口存在时暂缓 GUI 任务。这不是端口未联通，恢复窗口内的数据未删除，也未擅自确认丢弃。用户启动后如仍看到该窗口，需要先处理恢复窗口再进行 CAD 操作。未将本次状态检查描述为完整绘图能力通过。

交接：验证服务及临时占用 socket 均已停止；9875、9876、8000、4096、5173 全部通过实际 bind/listen 核对。用户继续运行原一键命令即可，无需配置后备端口。
