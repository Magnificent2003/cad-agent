# 实际工程复测与启动故障处理 · 2026-09-28

状态：**两组真实工程对照已完成，第一轮场布实验模块已撤回；保留模型网络和启动端口修复。** 上一轮用简单合成图和自动测试支持复杂施工场布成功，是验证范围判断错误。此次以真实交付文件为依据。

## 启动与 DeepSeek 连接

用户两次失败任务 `8d4778803d4d446bbd3c88332db222e8`、`93c011a6a9424f13a5182655d4464e76` 在任何 CAD 工具执行前报 `Cannot connect to API`；端点为 `https://api.deepseek.com/chat/completions`。比较故障进程和 `.env`：密钥、端点、模型相同，API 配置没有变化。故障进程在本轮修改前又能实际回答请求，因此不能事后将瞬时故障唯一归因于代理、密钥或几何代码。

已针对启动的不确定性修复：

- `agent/network.py`：启动时明确检验网络路径，默认直连，直连不可用才试配置的代理；选定后固定进程路由，本机服务始终绕过代理。API 地址和密钥保持原值。`.env` 与 `.env.example` 同步增加 `DEEPSEEK_NETWORK_MODE=auto`，支持显式 direct/proxy。
- `agent/launcher.py`：网络不可用时启动终端给出原因，成功时显示走直连或代理。配置检查与网络就绪不再混为一谈。
- 验证：把全部代理变量设为失效地址 `127.0.0.1:9`，直接启动真实完整项目，再提交白桥实际场布任务。引擎已通过直连持续生成真实 CAD 操作，不以 HTTP 探测代替模型实用结果。

端口现场有脱离启动器的孤儿进程：8000 的 python PID 1823，4096 的 opencode PID 1835。新版 `scripts/dev.py` / `scripts/ports.py` 在启动前仅回收配置服务端口：先让旧项目启动器清理，再 TERM/KILL 残留监听进程；WSL 可定位 Windows 监听者。不会按 python/node 名称全杀或重启 WSL。

已做真实冲突复现：Windows 临时进程监听 loopback 端口 10138，Linux bind 失败但 ss 看不到；脚本定位 Windows PID 并关闭，之后 Linux 成功绑定。Linux 拒绝 TERM 的监听者、连续重绑、旧启动器清理也已实际验证。新版一键命令已直接接管用户现场残留的 8000/4096 并启动 FreeCAD、后端、智能体和 Vite。

## 工程任务与判断口径

输入是用户的 v0009《建筑红线内_施工场地布置底图.dxf》，5,983 个实体，不是合成图。源文件：

`data/agent-tasks/786b4ced67ef4d1198bfe8bdf0359aee/input/drawing.dxf`

SHA-256：`20f23308dd1246ed6e8e60549b569ecce0408b166b76c153f3844f3a7ec906db`。

使用用户原要求：在中部最大空地布置塔吊（覆盖 7#～10# 厂房）、钢筋／模板加工棚、材料堆场、临时施工道路等，并生成场布建议文件。脚本 `engineering_retest.py` 只补齐原对话指代背景，不预先提供边界、单位或正确布局答案。两组必须使用同一脚本、输入和提示；标签 on/off 只记录实际启动版本，不暗中切换代码。

判断最终文件：是否实际交付必要设施；设施之间及与真实厂房是否重叠；道路有无实际宽度、自交及穿厂房；塔吊覆盖声明是否成立；图面标注是否可读，底图是否保留。未知尺度不擅自认定为已确认，工具 passed 不代替这些工程检查。

## 本轮实际结果与决定

**有局部改善，但整套实验方案不满足正式保留条件。** on 在这个样本中目标识别和道路避碰优于 off，这一事实保留；不能据单次随机生成结果认定整套模块的稳定因果收益。尤其两组都没完成用户要求的塔吊覆盖，而 on 的强制检查提供了不可靠的通过信号。决定撤回第一轮 `cad_domain/`、三个场布 MCP 辅助工具、强制交付检查、对应提示及测试；恢复 `04a88d5` 的自主 Python / FreeCAD MCP 执行链路。前端、项目历史、任务数据不回滚，网络与端口修复保留。参数化布局 `cad_layout` 在真实 on 任务中一次也未使用，不能将本例成果归功于它。

回滚不表示 off 成果合格，也没有解决施工场布能力本身。它撤掉的是当前不能可靠兑现的实验能力，避免继续把 passed 当作工程成功。原实现保存在 Git 提交 `2bd013d`，原开发记录已加撤回说明。

## 实测暴露出的具体缺陷

1. **检查对象可以漏掉关键建筑。** on 的检查清单最终只有 28 个可解析的闭合多段线，没有四栋真实目标厂房。检查器遇到 INSERT 中的附属 LINE、开放轮廓会直接失败，反馈又不够明确，模型反复过滤清单后通过。模型另做的手工几何检查不能替代检查器漏掉的范围。
2. **检查通过没有约束原始目标。** 用户明确要求塔吊覆盖 7#～10#，工具没有对应覆盖项，后端仍允许“场布复核通过”的成果发布。同一个文件哈希只证明版本一致，不能证明检查范围完整。
3. **图像看起来空白不等于几何空白。** 原图已有 WIPEOUT `6B00`，其平面范围完全盖住四栋目标厂房；模型空间绘制顺序中它位于厂房和编号之后，且没有 SORTENTS 重绘排序。平台按这一顺序预览时，这些厂房不可见。原轮廓与编号并未删除、图层也未关闭。off 因而把显眼的东侧另一组厂房当作目标。
4. **真实对象和坐标超出简单样例。** on 在封闭道路面与带宽中心线的表达上碰壁，高测量坐标的尺寸误差也触发过严格容差检查。最后靠修改申报尺寸／对象清单才能继续，不能把这样的过程描述为成熟工程能力。

四栋目标的对应关系另由原图编号验证：标签来自 INSERT `2F6` 内的 ANNO-ROOM 文本，世界坐标下分别落在 `1204`、`11EE`、`127A`、`1253` 的轮廓内部；不是仅凭面积猜编号。为避免遮罩影响判断，独立核验图只绘制从实际文件读取的几何，不改变原 DXF。
